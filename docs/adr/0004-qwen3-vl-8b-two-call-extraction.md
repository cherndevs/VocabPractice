# Use Qwen3-VL-8B via OpenRouter, with a two-call fallback, for spelling-list extraction

[0003](0003-gemini-over-claude-for-spelling-list-extraction.md) chose Gemini 3.6 Flash over Claude to avoid a separate Anthropic Console billing account. Once real usage was measured, Gemini's cost turned out to be the weaker part of that tradeoff: it's a thinking model, and hidden reasoning tokens bill at the output rate, so real cost came to $0.005–$0.014/image against Claude's flat $0.003 — even though free-tier volume meant this project wasn't actually paying either way. Cheaper, non-Chinese-specific options exist and were worth checking before settling.

Qwen3-VL-8B-instruct via OpenRouter was tried next, chosen for being small, cheap, and vision-capable with a genuinely free-to-cheap OpenRouter account (no separate provider billing relationship, same as the Gemini appeal). On the English test worksheet, a single call with a strict JSON schema response format returned all 24 words correctly for $0.000354 — roughly 10x cheaper than Claude.

On the Chinese test worksheet, the same single-call approach returned `{"candidates": []}` — a schema-valid but wrong empty result, not an error. This was isolated, not assumed: the same photo, same model, with the JSON schema removed and a free-form text prompt substituted, correctly read all three units including 考一考 (the homophone-risk word from [0002](0002-server-proxy-for-image-extraction-no-persistence.md)'s validation history). So the model could read the image; something about combining vision input with a strict schema response broke specifically on this harder/longer Chinese content. Turning off `strict` didn't fix it. Switching to `qwen3-vl-8b-thinking` (a separate model, not a flag) did produce non-empty output, but introduced a different error — it substituted 本子 (notebook) for 本书 (book) in one sentence — and cost 24x more per call ($0.0085), since its reasoning tokens bill the same way Gemini's do.

The fix that actually worked: split extraction into two calls. First, a free-form vision call with no schema — reads the image, replies in plain text. Second, a text-only call (no image) that reformats that plain text into the strict JSON schema. Run against the Chinese worksheet, this produced all 22 words correctly, including both risk lines, for a combined $0.00047 — cheaper than the single failed structured-output attempt would have cost if it had worked, and far cheaper than every other model tried.

This two-call shape is only needed as a fallback, not the default path: the single structured-output call worked correctly on the English worksheet and is the cheaper, faster path when it works. Since a genuinely blank worksheet photo and this structured-output collapse produce the identical response (`candidates: []`), there's no way to distinguish them from the response alone — so the extraction function always retries via the two-call path when the fast path returns empty, at the cost of one extra cheap call in the genuinely-blank case.

The architecture from [0002](0002-server-proxy-for-image-extraction-no-persistence.md) is unaffected — stateless server-side proxy, key in a Render env var, nothing persisted. Only the provider (OpenRouter), model (`qwen/qwen3-vl-8b-instruct`), request/response shape, and env var name (`OPENROUTER_API_KEY`) changed, plus the addition of the fallback path itself.

## Considered Options

- **Gemini 3.6 Flash** (chosen in 0003) — superseded: accuracy was fine, but real per-image cost was the highest of everything tried, due to billed thinking tokens.
- **Qwen3-VL-8B-instruct, single call, structured output** — rejected as the only path: cheapest option and correct on English, but silently returns an empty (schema-valid, wrong) result on harder Chinese content. Kept as the fast path, not removed, since it works correctly most of the time and the two-call fallback only triggers when it doesn't.
- **Qwen3-VL-8B-thinking, single call, structured output** — rejected: fixes the empty-result collapse but introduces its own transcription error (本子→本书) and costs ~24x more per call than the instruct model, for a worse result than the two-call approach below.
- **Qwen3-VL-8B-instruct, two calls (free-form extraction, then text-only formatting)** (chosen, as fallback) — most accurate and cheapest option found when the fast path fails. Not used as the default path because it's unnecessary overhead (an extra network round-trip) for the common case where the single-call path already works.
